### Harness capabilities and portability

The package is intended to work across harnesses that can carry out the common workspace agreement. Named hosts are reference configurations for validation and optional setup examples; they do not define a closed list of agents permitted to use the story directory. T9's Codex-then-Claude order establishes where to demonstrate the workflow first. T10 selects Pi with native OpenRouter support as the additional reference pairing. The writer skill itself remains harness-agnostic.

The existing scope already calls for portable conventions and distinguishes documented from observed behavior. This checklist consolidates the capability requirements behind those conventions. It is a design/documentation checklist, not a proposal for a general host-adapter registry or automatic capability-detection framework.

#### How the skill adapts to available capabilities

**Author requirement.** The main writer skill and its capability-routing reference must be agnostic to the user's agent harness. They describe the common writing, persistence, conversation, recovery, and browser-file agreement, then ask the agent to establish what it can do and how to do it in its actual session. They must not dispatch the workflow by harness brand, assume that a named tool exists, or require a known-host adapter before the agent can operate the directory. This is guidance interpreted by the existing agent, not another executable router or agent runtime.

The routing guidance should:

1. Establish the actual tool surface, permissions, shared workspace access, and available helper runtime. Use exposed tool descriptions, relevant host settings, and documented/observed behavior rather than inferring capabilities from a product name or the model's recollection.
2. Explain the applicable local-wait pattern: an ordinary command whose result returns to the writer, a yielded command that must keep being serviced, or an available native event/monitor mechanism. Keep the public logs and writer behavior the same across these paths. A background process is not sufficient evidence that input will return control.
3. Have the agent determine the concrete tool invocation, lifecycle limits, and hook setup from its actual tools and available local help or current documentation as needed. Describe what each operation must accomplish rather than routing to a prescribed implementation for a named harness. Establish the applicable mechanism at setup/reentry and revisit it when the environment changes; do not add repeated capability research to every story exchange.
4. Explain reduced guarantees when a capability is missing. Use normal host controls or human assistance when needed; a Markdown instruction cannot create an absent event, permission, or continuation facility. Keep observed support distinct from a plausible untested route.

Native checkpoint wiring is the part that may require more than Markdown: the host's hook configuration and a command calling the shared Git check, or a small native extension where that is the supported mechanism. The common reference describes the required completion-event behavior, the shared check's interface, and the need to establish activation and verify execution. The agent determines how its harness can supply that behavior, subject to normal host permissions and trust. The host must actually execute it; ordinary writer instructions cannot enforce a completion event themselves.

Concrete reference-host setup, hook definitions/extensions, provider instructions, and observed tool details belong in separate setup and validation materials. They can document reproducible examples for Codex, Claude Code, and Pi, but must not become harness-name branches or prerequisites in the core writer skill. Verification must exercise the same capability-driven skill in each reference host, rather than replace it with a host-specific writing loop.

Exact guide filenames and reference-host configuration files will be listed in the detailed implementation plan. This clarification does not adopt a registry, general native-tool registration system, separate provider client, or another writing loop. Pi's selection in T10 is a reference-validation choice and does not specialize the common skill for Pi.

#### Impeccable precedent for capability-driven guidance

The author identifies Impeccable as inspiration for letting the existing agent establish its capabilities and determine how to carry out the workflow. A read-only inspection of the installed Impeccable 4.8.0 instructions confirms concrete examples of conditional tool use and fallbacks:

* Its main skill (`Impeccable skill: SKILL.md`) defines a fallback when its context launcher cannot run: read existing project context directly and continue the permitted work. Launcher failure does not automatically end the workflow or justify inventing missing context.
* Its visualization reference (`Impeccable skill: reference/visualize.md`) accommodates native image generation or a reported API fallback, and directs image conversion through tools actually reported as available, with a limited probe when none were reported. The operation stays defined while the available means vary.
* Its new-work reference (`Impeccable skill: reference/new-work.md`) provides an inline documenter path when native subagents are unavailable. The inline documenter instructions (`Impeccable skill: reference/degraded/documenter.md`) explicitly disclose that substitution. A fallback does not silently claim the same execution conditions.
* Its Live reference (`Impeccable skill: reference/live.md`) uses structured helper results to identify the applicable situation and available authoring mode rather than relying on a framework guess. This supports describing a shared operation and letting the agent use concrete evidence to determine the method.

There is a relevant limit to the analogy: the installed Live reference also explicitly prescribes different waiting behavior for Claude Code, Cursor, Codex, and other harnesses. Impeccable therefore supplies both capability-driven patterns and named-host instructions. CouldHappen carries forward the former under the author's stricter constraint: the core skill asks the agent to establish the required behavior using its actual capabilities; named-host details remain separate reference setup/validation evidence.

Impeccable also ships a self-contained helper executable according to its main skill. That is evidence that reusable agent instructions can depend on a concrete supplied helper interface while adapting how the host invokes it. It does not select CouldHappen's helper packaging or runtime. This inspection ran no Impeccable design/build flow, changed no installed skill files, and did not regenerate the selected visual reference.

#### Capability needed for native checkpoint enforcement

To deliver T7's completion-hook assurance, the host must additionally expose a reachable end-of-work event that can run the concrete Git check and request continuation when relevant changes remain uncheckpointed. The hook must be installed, permitted, active, and tested on the actual surface/version. A passive notification event does not satisfy that requirement.

A harness without that facility can still run the ordinary file-based play workflow and follow the deliberate-close checkpoint instructions. Its checkpoint behavior is guidance-only at boundaries lacking enforcement, and must be described that way. This does not remove the requirement to provide and validate supported checkpoint hooks in the adopted reference integrations. It also does not justify building a replacement agent controller to manufacture a missing host event.

#### Capabilities that remain optional or route-specific

Native skill discovery, native monitors, background completion notifications, PTYs, delegation, image generation, saved host chat, and dedicated custom-tool registration are not individually required. At least one workable input-wait path is required; the agent establishes which path its actual tools can support under the common guidance. Delegation adds the obligation to account for delegated writers during recovery; it is not a prerequisite for play.

OpenRouter access is required in at least one supported reference route, using existing host/provider configuration and human-selected models. It is not a prerequisite for every user running a normal host account. Character-card PNG/JSON handling can use the supplied local tools/helpers; native image generation or a particular image provider is not required for the first scene.

Describe other harnesses by the capabilities and limitations actually established. Reserve a demonstrated compatibility claim for an observed host surface/version/model pairing. The common skill, story records, public agreement, and helpers remain portable; concrete hook wiring varies with the host. Reference-host setup and validation materials document those differences separately from the harness-agnostic skill.

### Decision T1: coordinating shared-log saves — A selected

The selected approach retains one shared Story log and one separate Director log. It introduces no separate inbox, universal one-outstanding-input rule, or private-world schema. The writer-controlled prose-production block remains separate from the saving mechanism. The alternatives below preserve the decision rationale; B is not the planned save path.

The concrete failure to prevent is an old writer copy replacing a log after a browser submission has already been saved. Checking whether a file changed and then saving it without coordinating the final write still leaves a race. Disabling a browser button alone also cannot account for a submission already being saved.

#### A. Pause submissions for a direct-edit interval — selected

**Author decision.** The writer controls when the browser may edit the shared logs. The browser/file bridge enforces that permission for actual saves, including requests already in progress when the writer asks for a pause. This controls browser writes; it does not grant new authority to revise established fiction without a Director instruction.

**Mechanism.** Before editing either shared log, the writer asks the browser/file bridge to pause submission saving. The bridge finishes any save already in progress and acknowledges the pause before the writer rereads the current logs. The writer then edits with ordinary file tools or scripts. After the edits are readable and valid, it releases the pause. Attempts to submit during the pause receive a clear unsaved result and retain their browser draft. The pause must affect actual submission acceptance, not only the visible controls.

**Trade-off.** This preserves direct editing of the authoritative logs and needs no general update or merge API. Both submission channels are unavailable during that edit interval, even for a short Director-log edit outside prose composition. Private note or method work does not require the interval. A prose-production block can cover the same time, but its purpose and lifetime are distinct.

**Failure conditions.** It depends on cooperation: the writer must obtain the acknowledgment, reread afterward, and keep other writers or delegates from touching the logs during its edit. An interruption can leave the pause in place. Recovery must establish that the previous writer has stopped editing before clearing it; a timeout alone cannot establish that. Browser reading must also tolerate incomplete saves without replacing a valid displayed view with broken content.

#### B. Apply shared-log updates through a small helper — not selected

**Mechanism.** The writer prepares prose or revisions with its chosen tools, then gives an update to the same local file helper used for browser submissions. The helper serializes the actual log writes. Adding a new entry preserves the current log; changing an existing entry checks the version being revised and reports a conflict rather than overwriting newer content. Exact entry identity, update syntax, and conflict checks remain to be designed if this option is selected.

**Trade-off.** Browser submissions can remain available during ordinary log updates unless the writer has separately engaged its prose-production block. The helper needs an update interface and conflict behavior. Authoring tools remain flexible, but the final save to an authoritative shared log must go through the helper; direct replacements outside that agreement are unsupported. This is a narrower public save path than option A and requires explicit author acceptance.

**Failure conditions.** Direct writes that bypass the helper defeat its protection. Conflicting revisions need writer attention. A successful file update does not prove that the writer has read or applied another pending human instruction. Helper interruption and browser retries must not duplicate a saved submission; their precise handling belongs to the subsequent input-recognition design.

Neither option guarantees safe arbitrary overlapping writes from unrelated tools. The author chose the cooperative pause around direct editing, retaining ordinary authoring tools and a small helper boundary. Already-submitted instruction timing, stale-block recovery, Undo, checkpoint hooks, public convention changes, and host selection remain separate decisions.

### Decision T2: handling already-saved input across both logs — C selected

The selected pause prevents new overlapping browser saves after acknowledgment. It does not decide how to handle entries saved before that pause. For example, a player action may be followed by a Director preference while the writer is maintaining private notes and submissions remain open. Both entries can be safely saved before the writer starts its next passage.

**Author decision.** The writer reads pending inputs from both logs together, combines compatible guidance, and decides what to answer or act on next. There is no mandatory cross-log submission order or Director-first scheduler. Explain consequential deferrals or conflicts in Director discussion, and ask when incompatible instructions cannot be resolved from context. Ordinary Director discussion remains distinct from permission to advance fiction.

The writer checks both logs for unread human entries before beginning the next story continuation. A successful browser save means the entry is on disk; it does not mean the writer has read, acknowledged, or applied it. Writer prose, log revisions, and reveal animation must not be mistaken for new human input. Stable input recognition and recovery bookkeeping remain to be specified. The comparison below records the alternatives; only C is selected.

| Option | Mechanism | Trade-off and failure condition |
| --- | --- | --- |
| A. Follow save order | Handle human entries in the order their saves were accepted across both logs, preserving that order in discoverable metadata. | Predictable ordering, but a later Director preference may arrive too late to affect an earlier queued action. Requires an ordering convention across the two files; timestamps alone can be ambiguous. |
| B. Address Director input first | At each new-work boundary, address unread Director entries before deciding what to do with pending story actions. Preserve order within each log. | Gives corrections and preferences priority over the next continuation, but sustained Director discussion can defer story actions. Director discussion still does not itself authorize advancing fiction. |
| C. Let the writer interpret the pending inputs together | Read both logs, combine related guidance where appropriate, and use writer judgment to decide what to answer or act on next. Explain consequential deferrals or conflicts in Director discussion. | Keeps coordination in the writer rather than requiring a fixed cross-log scheduler. Ordering is less predictable; the writer may misjudge intent and must ask when conflicting instructions cannot be resolved from context. |

None of these policies promises interruption of prose already being composed. Explicit Undo must follow the recovery procedure and the accepted wait for new Director direction; save order or writer discretion cannot make old pending story input automatically resume a rejected continuation. Handling interrupted blocks and the recovery procedure remain separate decisions.

### Recovery constraints carried forward

The following constraints apply regardless of the session choice in T3. They restate accepted recovery outcomes; they do not select restore commands, helper state formats, or automatic coordination machinery.

1. Establish a quiet editing boundary before restoring relevant files. Use T1's acknowledged pause for browser writes, and account for the writer's own work and any delegated work that could overwrite the recovery. If the existing host cannot establish that work has stopped, use its normal controls with human assistance rather than claiming a safe restore. A helper's reachability or an elapsed timeout cannot establish quiescence.
2. Inspect available Git checkpoints and relevant current changes. Explain the actual recovery scope and distinguish recorded restoration from reconstruction. Preserve applicable Director guidance and preferences, plus useful method/interface improvements by default, without retaining rejected fictional assumptions in them. Mixed commits and untracked or external materials can limit what is recoverable.
3. Reconcile the restored story and working records with the browser/helper view and the current public conventions. Previously pending input cannot automatically authorize another story continuation. Preserve enough of the recovery explanation and human guidance to make the next session or resumed writer understand the supported result. Exact retained files and input bookkeeping remain part of the public-agreement design.
4. After restoration, ask for Director direction and wait. Reading restored files or reopening the browser does not itself authorize replacement prose. The mechanism must allow new Director input while keeping old pending story input from resuming the rejected continuation.

An interrupted direct-edit pause follows the same basic requirement: establish that the former editor is no longer writing, inspect the actual files, and reestablish a usable browser view before allowing writes again. The interface must not silently clear a pause merely because it appears old. The host-specific assistance and commands remain to be designed and observed.

### Decision T3: writer context after Undo — A selected

**Author decision and rationale.** Continue in the current writer session after Undo. Remembering the attempted continuation is useful: the writer can understand what the human did not want, interpret subsequent Director feedback, and try a different approach when continuation is authorized. The goal is to withdraw the attempt's authority as fiction, not to erase the writer's knowledge that it tried that approach.

The writer rereads the restored story and working materials, retains applicable human corrections and preferences, and treats the withdrawn development and its associated assumptions as no longer established events, disclosed claims, or current private explanations merely because they appeared in the rejected attempt. It may use knowledge of the rejection to inform its creative approach. A remembered attempt must not count as something the player's character experienced or learned in the restored story.

After reporting recovery, the writer asks for Director direction and waits. That new guidance may explain the rejection, request a different approach, or direct another action; remembering the prior attempt does not itself authorize automatic replacement prose. A fresh compatible session remains a fallback when needed or requested, rather than a required part of every Undo. The comparison below records the alternatives; only A is selected.

| Option | Mechanism | Trade-off and failure condition |
| --- | --- | --- |
| A. Continue in the current writer session, with a fresh-session fallback | The current writer rereads restored materials and retained human guidance, explicitly treats the withdrawn development and its assumptions as no longer authoritative, reports recovery, and waits. Use a fresh compatible session if the live session cannot resume coherently or the Director requests it. | Keeps ordinary Undo within the Director conversation and preserves useful knowledge of what was tried. The failure is accidentally reusing rejected story facts as current truth, rather than remembering the attempt as feedback. |
| B. Require a fresh writer session after each Undo | After the editing boundary and recovery record are established, hand continuation to a fresh compatible session using the restored workspace and retained guidance. That writer verifies the recovered view, asks for Director direction, and waits. Host-specific steps must establish that the previous session and relevant delegated work cannot keep writing. | Reduces dependence on the old conversation context, but every Undo requires a session transition and potentially human host assistance. A new context does not repair incomplete records or stale assumptions retained in files, and starting it does not automatically stop the old writer. |

The selected approach deliberately retains awareness of the rejected attempt. It does not promise literal removal of rejected material from live context. The separate requirement to observe fresh-context continuation remains. No browser Stop control or workspace-owned session supervisor is introduced.

### Decision T4: changing public conventions — A selected

**Author decision.** For an incompatible public change, the writer pauses browser writes, updates the affected files and components together, reopens the affected readers/helpers, verifies the current view, and then resumes submissions. The writer chooses when to perform this maintenance. A stale browser/helper must not keep writing under the superseded agreement. The comparison below preserves the alternatives; only A is selected.

**Author clarification: cast content remains ordinary story work.** The writer is free to invent new characters, develop existing ones, and choose which names and available portraits are publicly disclosed, consistently with the story. Supplied character cards are starting material, not an exhaustive cast or a requirement for creating a character. Adding or revealing a character, changing cast membership, or selecting an available portrait does not require the maintenance pause or component restart discussed here. Normal safe-saving rules still apply to any shared-log edits involved, and importing a card alone still does not disclose its character.

Private note reorganization and ordinary presentation changes can likewise remain writer-managed work. T4 concerns changes to the agreement that running components understand: for example, changing log syntax or locations, the format or discovery location of public cast data, input-recognition metadata, or the meaning of browser-write permission signals. Changing the cast data's contents within the existing agreement is not such a change. An old browser tab might fail to understand a new data format or still submit using a format that the updated file bridge no longer accepts. T1 prevents overlapping writes, but does not by itself make old and new conventions compatible.

| Option | Mechanism | Trade-off and failure condition |
| --- | --- | --- |
| A. Pause and reopen for incompatible public changes | The writer chooses when to make the change, pauses browser writes, updates the affected files and readers together, then reloads or relaunches the relevant browser/helper parts and verifies the current view before reopening submissions. Keep the current public agreement discoverable. | Allows public conventions to evolve without requiring live compatibility machinery. Play briefly pauses; stale clients must be refused rather than allowed to write using the old agreement. Interruption partway through the change requires completing or reverting it before reopening. |
| B. Support a live changeover between public conventions | Identify the convention used by each active client and provide explicit compatibility or conversion for the particular change while old clients remain active. Preserve drafts and report an incompatibility when conversion is unavailable. | Can keep play available during supported changes, but adds compatibility logic and a period with multiple representations. Incorrect conversion or an unrecognized old client can misinterpret input or displayed material. Unsupported changes still need a pause; no general migration engine is assumed. |

This choice concerns incompatible public changes, not cast additions or updates, every skill edit, private record move, or visual adjustment. It does not make infrastructure immutable or add a standing requirement to seek human approval for routine writer-managed maintenance. Hook changes still have to respect the host's own activation and trust behavior. Compatibility checking must also account for restored story files and retained interface improvements during Undo.

### Decision T5: the shared-log representation — A selected

**Author decision.** Use Markdown conversations with normal prose paragraphs and small machine-readable entry metadata. Identity, author role, and explicit boundaries support input recognition and display without storing multiline prose as escaped JSON strings. The exact boundary syntax and validation rules remain to be specified. The comparison below records the alternatives; only A is selected.

T1 permits ordinary direct file editing within an acknowledged pause. The logs also need enough structure for the browser and local wait to distinguish new human entries from writer output and authorized revisions. A file modification by itself is not an input event.

The public agreement needs to identify each entry and its author role, delimit its content, and keep an existing entry's identity when its text is revised. The writer's processing state must distinguish pending human input from input already addressed or deliberately deferred, sufficiently to support restart and Undo. A browser save acknowledgment establishes persistence only; it does not establish that the writer applied an instruction. T6 addresses where processing bookkeeping lives; entry syntax and validation remain to be specified.

| Option | Mechanism | Trade-off and failure condition |
| --- | --- | --- |
| A. Markdown prose with entry metadata | Keep each conversation as a Markdown document. Use explicit entry boundaries and small machine-readable metadata for identity and role; keep the prose itself as normal paragraphs. Browser and wait readers interpret those boundaries. | Comfortable to read, edit, and inspect in Git using ordinary text tools. Requires a defined boundary syntax and parser behavior. Broken or duplicated metadata, or prose that accidentally resembles a boundary, must be detected rather than treated as new input. |
| B. JSON Lines entries with Markdown text | Keep each conversation as one file containing one JSON record per entry. Each record carries identity, role, and the text body. Browser display renders the body as prose; the file reader uses the JSON structure. | Uses a conventional structured representation and makes entry fields explicit. Multiline prose is stored as an escaped string, making direct source reading and long prose edits less comfortable. Malformed records or duplicate identities must still be detected; structured storage does not itself make a save safe. |

Both options retain a single authoritative Story conversation and a separate Director conversation. Neither requires an append-only writing method, a second canonical manuscript, or a schema for private world records. Director-authorized revisions remain possible through T1's direct-edit interval. Readers must tolerate a save in progress without turning partial contents into a new submission or replacing a valid displayed view with broken content.

### Decision T6: where input-processing bookkeeping lives — A selected

**Author decision.** Keep input dispositions in each human entry's Markdown metadata, alongside its stable identity and role. Preserve the human's message body when updating processing metadata. The conversations remain the authority for which inputs are pending, addressed, or deliberately deferred; no separate per-input status file is required. The comparison below records the alternatives; only A is selected.

The writer may interpret inputs together and address them out of submission order under T2. A single last-read position is therefore insufficient by itself: an older unresolved message must not disappear merely because a newer one was answered. The public bookkeeping needs to identify which human entries remain pending, which were addressed, and which were deliberately deferred. These are writer-reported dispositions, not proof that an instruction was followed successfully or that a preference has been applied forever.

| Option | Mechanism | Trade-off and failure condition |
| --- | --- | --- |
| A. Store dispositions in the Markdown entry metadata | The writer updates the small metadata associated with each human entry while preserving its identity and original message body. Browser and wait readers derive pending input from the logs themselves. | Keeps message content and processing state together, with fewer authoritative files. Bookkeeping requires editing the shared logs under T1's pause. An accidental metadata change or Git restore can change which entries appear pending, so interrupted work and Undo still require reconciliation. |
| B. Keep a small public work-state file keyed by entry IDs | Leave message metadata focused on identity and role; record dispositions against those IDs in one small work-state file used by the writer and local wait. The actual human messages remain exclusively in their Markdown conversations. | Avoids revising log entries just to update their processing state and can share a file with other public work-state information. Adds a file that can disagree with the logs after an interrupted save or restore; missing or inconsistent state must trigger inspection rather than blind replay. |

Neither alternative creates a separate message inbox or prescribes the writer's private records. Neither makes prose saves and disposition updates one indivisible transaction. If an interruption leaves it unclear whether an input already produced a response, the resumed writer must inspect the actual conversation and working materials before deciding what remains to do. Do not claim automatic exactly-once processing. After Undo, old pending input remains subject to the separate requirement to wait for new Director direction, regardless of its stored disposition.

**Selected behavior.** Processing-metadata edits use T1's acknowledged direct-edit interval. They do not constitute new human messages, authorize revisions to human prose, or replay the browser's reveal animation. A deliberately deferred entry remains discoverable without repeatedly waking the writer as new input; the writer can reconsider it alongside later guidance. An addressed preference can still apply to future writing through durable writer-managed records. Its disposition means the submission was handled, not that the preference has expired or that its application has been verified automatically.

### Decision T7: when checkpoint checks enforce a save to Git — A selected

**Author decision.** Enforce the concrete checkpoint condition at deliberate session closure and supported host completion. Do not impose a checkpoint interval or deadline during continuous play. The writer chooses meaningful commit timing within the play stretch. The comparison below records the alternatives; only A is selected.

The writer continues to choose meaningful commit timing. A concrete checkpoint check can detect changes in the agreed Git scope and require the writer to resolve them before proceeding past an enforcement boundary. It cannot decide whether important facts were recorded or a continuation is believable. The exact scope must include relevant story and method materials while excluding transient runtime files and credentials; it will be enumerated in the detailed plan.

The earlier host investigation notes that a host turn can span several story exchanges. A hook at host completion is therefore not automatically a hook after each story response. Hook definitions also need activation under the host's normal trust behavior. None of those boundaries has been observed working for this package yet; the selected policy is a design requirement, not a compatibility claim.

| Option | Mechanism | Trade-off and failure condition |
| --- | --- | --- |
| A. Enforce at deliberate session closure and reachable host completion | Writer guidance requires a checkpoint check when deliberately ending a play stretch. An active supported completion hook checks the same concrete Git condition when the host is actually finishing work and requests continuation if relevant changes remain uncheckpointed. #### Framework trade-offs for the agent writer

The useful question is how easily the writer can understand a change, make it locally, get actionable feedback, and recover if the interface behaves incorrectly. Minimum framework size and absence of compilation do not alone determine that experience. The following are engineering judgments for this project's proposed interface, not measured comparisons of model coding accuracy.

| Writer task | Alpine | Preact | Svelte with Vite |
| --- | --- | --- | --- |
| Make a small interface adjustment | Direct edits to HTML and ordinary JavaScript; little setup. | Edit a component in JavaScript/HTM or JSX, depending on the chosen tooling. | Edit a small component containing its relevant markup, behavior, and styles. | Keep several views and controls consistent | Shared state and larger behavior need deliberate organization as markup grows. | Components and explicit state transitions can organize the reader, Director view, cast, and composer.
