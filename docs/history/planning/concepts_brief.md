## Overview

CouldHappen supplies a portable project directory that an existing agent can use as an author and game master. The human opens that workspace in a supported agent, asks it to launch the supplied editable browser interface, and plays through a shared story conversation file. The browser records human story input; the writer reads it, develops the continuation, maintains its own records, saves prose to the same conversation, and waits locally for more input. Director discussion has a separate conversation and does not automatically advance the fiction.

The package starts with skills, supported hooks, templates, durable records, and the small local helpers needed for browser file access and waiting. The existing host owns model calls, tools, permissions, and the agent session. Claude Code and Codex are required support targets. At least one supported existing-host route must offer the human's choice of underlying model through OpenRouter; OpenCode, Pi, Hermes, and DeepSeek Harness remain candidates rather than four additional adopted integrations.

Begin with the accepted short-scene demonstration: a world prompt and imported character cards, supplied card PNGs in a cast panel, several browser story exchanges, a Director exchange, and an unwanted continuation undone through the writer's available Git checkpoints. The writer explains recovery limits, restores the supported scope, then asks for Director direction and waits. A complete mystery arc is a later demonstration. No story image generation belongs in the first scene. The actual Impeccable direction round is complete: the user selected Woven anthology, retaining the comp-led approach. Its selected reference is [.impeccable/mocks/decision/woven.png](../../designs/woven/woven.png). Interface mockup imagery remains separate from runtime story imagery; see docs/designs/impeccable_direction_notes.md for provenance and interpretation.

This brief draws on [brainstorming_notes.md](brainstorming_notes.md) and its four supporting investigations. Six independent BRAINSTORM reviews are synthesized in [goldfish_review_report.md](../../reviews/goldfish_review_report.md), with individual reports under goldfish_reviews (`goldfish_reviews`, kept locally, not published). They found no concept-level Blocker, but did not establish that the proposed capabilities work. Their recommendations remain proposals for user alignment.

## Analysis

**What is established and what is assumed.** Source inspection and the user's experience support basic browser-to-existing-agent handoff precedent. The current investigations did not run this workspace's story loop, checkpoint hooks, recovery, or OpenRouter pairing. A running helper is not evidence that a host continues servicing its results. A hook file is not evidence of an active trusted hook. A commit is not evidence that all important story knowledge was recorded. Fresh-context continuation is a required outcome whose quality remains to be demonstrated.

The concept transfers work from an application-owned controller into the existing host and writer-managed files. That can reduce owned code substantially. The strongest opposing argument is that waiting, two shared conversations, safe saving, editable conventions, and restoration could spread controller-like responsibilities across scripts, hooks, browser code, and skills. Calling them files does not make the coordination free. The package must earn its small size by choosing limited, understandable behavior rather than adding a supervisor for each ambiguity.

**Accepted user requirements.** The human can play a character, contribute prose, and separately act as Director. One writer can portray the whole cast; host-supported delegation is optional. Worlds and genres stay open. Player influence and consequences should be meaningful and believable. Established events, disclosed claims, private plans, and possible developments must remain distinguishable, but their private storage is the writer's choice. A hidden explanation may change to improve a believable continuation consistent with established and disclosed material; neither the writer's original plan nor a player's theory automatically determines the truth.

Director discussion is constructive back-and-forth that may inspire both parties, shape preferences and methods, or influence later writing without automatically advancing fictional time or establishing hypotheticals. Explicit Director instructions can authorize continuation or revisions. Preferences can be given naturally; the writer records and applies them and may reorganize its methods. A fixed preference-injection system is not required. It reads useful portions of its previous prose for voice, pacing, and continuity.

Imports are Director actions, including during play. SillyTavern PNG/JSON sources and supplied portraits are preserved. Cards establish initial identity by default, with later development and stricter adherence preferences possible. Compatible adaptation is autonomous; genuine conflict between initial identity and an explicit world premise asks for Director guidance and retains the resolution. Greetings, example dialogue, scenarios, and roleplay instructions are source material, not automatic events or governing writer instructions. Import does not itself reveal a character in the public cast.

The writer can edit skills, write scripts, use available file tools, and reorganize its private records. It must leave discoverable knowledge for continuation after context loss or restart: characters, established/disclosed material, private possibilities, prose, preferences, retained Director guidance, and a way to find its current working notes. Saved host chat context is welcome but optional. The growing conversation must not become the primary world representation, and private model reasoning need not be saved.

**Accepted presentation and recovery trade-offs.** New prose is saved normally and revealed through browser animation; the writer understands that behavior and chooses its editing methods. Established prose changes only on Director instruction. Authorized revisions may update immediately, with a changed-passage indicator desirable if inexpensive. This is file-driven presentation, not a raw model-token stream or a disk-writing animation requirement. The prose-writing submission block applies to player actions as well as Director messages, under the same writer-controlled arrangement. The writer controls engaging and releasing it. Private workspace work does not by itself require a block, and a saved response's reveal animation is separate from writing. Browser Stop is deferred. Accept/Revise controls are removed.

Git includes prose and relevant story materials. The writer chooses meaningful commit times, with supported hooks intended to ensure changed work is checkpointed. The useful concrete condition, enforcement event, and activation path remain unresolved. The user accepts that available commits limit Undo precision: a checkpoint may span several exchanges or one interaction may include several commits. The writer must describe what history supports, distinguish reconstruction from historical restore, retain applicable corrections/preferences, and wait for Director direction after restoring. Exact per-interaction recovery is not promised. Git does not remove rejected material from a live model context or automatically cover untracked/external material.

The user has settled the default scope: preserve useful skills and interface improvements when undoing an unwanted story development. The Director can explicitly ask to undo those improvements too. Retained methods must not keep rejected fictional assumptions as current story authority. If commits mix story changes and improvements, the writer explains what can be separated and labels any reconstruction honestly. This does not require a blanket workspace reset or guarantee exact selective recovery from every checkpoint.

**Reviewer proposals and subsequent alignment.** The strongest shared objection is the public log boundary. A browser append and an old writer replacement can erase input; a file change can be misread as a new human action. The user has now said the writer disables player-action submissions while making a prose reply, using the same arrangement as Director chat. This addresses ordinary submissions during the blocked phase. Cooperative safe saving, short edit intervals, and serialized particular writes remain possible ways to handle other overlaps; no mechanism is selected. A separate inbox would change the working shared-log proposal and requires discussion. Writer freedom does not establish transparent safety for arbitrary overlapping whole-file saves.

A related proposal concerns timing: saving a Director instruction while input is open is different from the writer reading, acknowledging, or applying it. An in-flight passage may finish first. The current brief applies the writer-controlled prose block to both submission channels, but does not select a universal one-outstanding-input rule during all work, immediate interruption, or a cross-log scheduler. Already-submitted messages and stale blocking after interruption still need handling.

All six lenses, in different ways, challenge recovery coherence. A restored log can disagree with a helper's handled-input position, an old browser copy, queued story input, a writing signal, or running delegated work. Reviewers propose an explicit quiet recovery boundary, retained Director discussion, a surviving explanation of what changed, and re-establishing the restored view before claiming success. Old pending story input must not bypass the accepted post-restore wait for new Director guidance. Assisted Undo with a reload may be enough. Automatic coordination, a fixed journal, session reset after every Undo, and a branching interface are not selected.

Other proposals are to maintain an obvious reentry pointer after record reorganization; keep the current public browser/writer/cast conventions discoverable; and treat incompatible convention changes deliberately, perhaps between play stretches. Public interoperability and freely chosen private methods have different compatibility effects. These proposals do not adopt a fixed world schema, immutable infrastructure, migration framework, or mandatory authoring tool. The user's default of retaining useful skill/interface improvements during Undo is now accepted; exact restoration and compatibility handling remain open.

**Assumptions and evidence still needed.** The ordinary waiting loop, host servicing and idle overhead, checkpoint enforcement, exceptional-interruption experience, and fresh-context continuity remain unverified in the intended host surfaces. Quiet local polling does not prove negligible model overhead when waits expire or need servicing. Browser/helper reachability does not prove writer liveness. Reviewers favor plain, truthful save/error/last-reported status and a return-to-host instruction over a presence supervisor or custom activity dashboard. Director chat remains the main place for discussion of work, failures, and recovery; existing host diagnostics remain available.

Reviewers propose an early fresh-session continuation using the accepted scene's actual disclosures and Director guidance. Several uninterrupted exchanges can succeed on live context alone. Whether restart belongs in the short scene or a separate early observation remains unresolved. Observe resulting fiction, not merely notes or the writer's assertion of completeness. No fixed fact schema or semantic-completeness hook follows from this requirement.

Host and model choice add another trade-off. A shared helper with thin instructions may cover both required hosts; a native OpenRouter candidate might be simpler than a launcher route on one of them. No route has won. The support claim must distinguish documentation, actual surface/version behavior, hook activation, and model capability. Model selection through OpenRouter is required; universal reliability across its catalog is not. The design reviewer rates idle overhead Major while the debugging reviewer rates it Nit; they agree to observe it before adding instrumentation.

## Goals vs. Non-Goals

* **In-Scope Goals:** A trusted local fiction workspace operated through an existing agent; the accepted browser launch/wait/write/repeat workflow; shared human/writer story conversation and separate Director discussion; durable discoverable world knowledge and fresh-context continuation; natural preferences and constructive discussion; PNG/JSON card imports with preserved sources and appropriately disclosed portraits; a readable prose-first editable template with card PNG cast panel; normal saves and browser reveal; writer-chosen Git checkpoints with supported concrete hook enforcement; honest Director-led Undo and post-restore waiting; Claude Code and Codex support and one suitable existing-host OpenRouter route; adaptable initial guidance for later host/user image tools.

* **Out-of-Scope Non-Goals:** Building an agent runtime, workspace-owned provider controller, mandatory private-world schema, transcript-as-world model, saved private reasoning, or universal model conformance. Exact interaction rollback, per-response commits, automatic replacement prose after Undo, Accept/Revise, and raw token streaming are not requirements. Browser Stop, generated story imagery, a complete mystery arc, and a full branching-history interface are deferred. No default container, sandbox service, elaborate permission layer, custom activity dashboard, automatic updater, general migration engine, or mandatory multi-agent writing system is selected. Woven anthology is the selected visual direction. No frontend framework, runtime dependency, model version, first host, or implementation sequence is chosen here.

The user selected Woven anthology from the actual comp-led Impeccable direction round: a petrol/teal shell, saffron accents, pale cool reading ground, serif prose, clear sans controls, and restrained interlaced rules. The selected reference preserves the cast panel, separate Story/Director navigation, and removal of Accept/Revise. Its scene, portraits, and biographies are illustrative. Later composition refinement and Director/revision/failure states remain design work, alongside reduced motion, reading-position preservation, and narrow-screen cast access. The visual selection does not authorize implementation or runtime story image generation in the first demo.

## Key Decisions & Staging for Next Steps

**Accepted decisions to carry forward:** Existing-agent ownership; the intended browser/file wait loop; shared story conversation with a distinct Director conversation; writer-managed private methods and discoverable durable knowledge; fresh-context restart without saved host chat dependency; constructive Director discussion, import interpretation, and natural durable preferences; normal-save browser reveal and Director-authorized prose changes; writer-controlled blocking of both submission channels during prose production; Git with writer-chosen checkpoint granularity and honest Undo limits; ask and wait after restoration; required Claude Code/Codex and existing-host OpenRouter model choice; card PNG cast panel for the short scene; no Accept/Revise or browser Stop; deferred story imagery; the selected Woven anthology visual direction from the actual comp-led Impeccable pass.

**Questions carried into design and host validation:** How should already-submitted messages and interrupted/stale blocks be handled? What does acknowledgment/application of a Director instruction submitted while input is open mean? What manual interruption/reopen burden is acceptable? How should old pending story input and running readers be reconciled during Undo? What concrete checkpoint assurance can a reachable trusted hook provide? Are incompatible public-convention changes maintenance actions? Which host surface and existing OpenRouter route produce the smallest useful experience? Does restart belong inside the accepted scene or in a separate early observation? These remain explicit design/evidence questions rather than reasons to keep reopening the agreed creative scope. Reviewers have not silently decided them. A demonstrated host pairing must precede a compatibility claim. The default of retaining useful skill/interface improvements during Undo is settled; its detailed mechanics are not.
