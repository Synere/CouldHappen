## docs/designs/couldhappen.md

- **The skill's reference set is described incompletely.** The "Portable skill and references" row lists setup, capability assessment, writing, persistence, imports, browser agreement, recovery and future image-tool adaptation. The skill also ships `references/voice.md` (a dialogue-craft method the skill tells the writer to read before any entry with speech) and `references/what-this-can-do.md` (the "what can you do?" answer flow). The design names neither. The 2026-11-06 report raised `what-this-can-do.md`, and it is still missing.
- **The design's creative-practice examples point at a "planned" skill that already ships its own copy.** The design links `docs/designs/creative-practice-examples.md` (line 256, and "optional illustrations for the planned writer skill" under Additional Resources). That file still says "The future skill package may provide this as an optional `references/creative-practice-examples.md`". The skill now ships that file, and the two copies have already drifted: their opening lines and links differ. Neither copy says which one is the source.

## docs/designs/distribution-and-workspaces.md

- **The link check covers more than "relative" links.** Builder step 7 says it checks "every relative inline Markdown link". `scripts/build_release.py` `link_targets` also resolves root-absolute targets (`/path`) against the ZIP root and fails the build when they are missing. So an example such as `/api/assets/x.png` in shipped Markdown breaks the release. It also skips targets that start with `<` (an angle-bracket link destination) without checking them, which the design does not mention.

## docs/public-contract.md

- **A clean `close` keeps an active production block, which turns into "interrupted ownership" after a restart.** The contract says `close` refuses only while an edit pause is held, and then "disarms". `Bridge.control` `close` runs `state.update(owner=False, armed=False)` and leaves `production` as it was. Observed in a scratch workspace: after `block --on` and a successful `close`, `.couldhappen/control.json` holds `production: true`. A later helper start then treats this as interrupted (`self.interrupted`), and `writer claim` is refused with "Existing ownership requires explicit recovery". Within the same helper run, though, `claim` clears the block without saying so. The contract does not describe closing while blocked. This is the same gap the 2026-11-06 report found for `paused`, which was fixed by having `close` refuse.
- **`wait-view` does not refuse an unowned workspace while a pause is persisted, so `wait` can hang after a restart.** The contract says `wait-view` "refuses an invalid or unowned workspace" and that `wait` returns exit 2 on recovery or error. The code returns `{'entries': []}` whenever `state['paused']` is true, and only checks ownership, closing and validity after that. A restarted helper loads `paused: true` from `control.json` with `closing` true (observed). In that state `wait-view` returns an empty list instead of an error. So `wait --timeout 0`, the recommended standing wait, never returns, although the workspace needs `writer recover`.
- **`validate` does not always name the invalid file and line.** The contract says `validate` reports an error "naming the first invalid file and line". Log errors carry `story:<line>` or `director:<line>`, which name the channel rather than the file. Cast and work errors carry neither. Examples: `Unsupported cast format`, `Invalid disclosed cast fields`, `Unsupported work format`, and a raw `json` decode message for a malformed `cast.json` or `work.json`. Observed: a `cast.json` with `schema_version: 2` prints only `{"status":"error","message":"Unsupported cast format"}`.
- **`cast.json` accepts unknown top-level fields.** The contract defines `schema_version`, `characters` and an optional `portrait_button`. `files.snapshot` rejects unknown fields on a character but not at the top level. A `cast.json` with an extra `sheet` object validates (observed), and the extra field is passed through to every browser snapshot. This is inconsistent with "Malformed entries ... close saving", and the contract does not say that extra top-level fields are allowed.
- **`card.md` is not "a lossless plain-text copy of every field".** `cards.readable` reads only the `data` object of a V2/V3 card. Envelope fields outside `data` are dropped, such as `spec_version` and the top-level V1-style `name` and `description` copies that many SillyTavern exports carry. Observed: `spec_version` and the top-level `name`/`description` do not appear. In a lorebook entry that has both `comment` and `name`, `name` is dropped: the title uses `comment`, and `name` is excluded from the flags (observed). Text fields that are present but falsy, such as `0` or `false`, are also skipped.
- **`portrait` on a JSON-card import gives a raw OS error, not guidance.** The contract says a source "that is not an imported PNG card returns `error` with guidance to run `import-card` first". When `--source` is the `imports/<sha>/` folder of a JSON import, `cards.preserved_source` maps it to a `source.png` that does not exist. `bounded` then raises `FileNotFoundError`, and the message is the raw `[Errno 2] ...` text with an absolute path.
- **Vite's file-serving deny list does not repeat every name.** The contract says the deny list "repeats the same names" as the 403 middleware: `imports`, `public`, `.couldhappen`, `.git`, `.env*`, `START_HERE.md`. In `web/vite.config.js`, `server.fs.deny` lists `.env*`, `.git`, `.couldhappen`, `imports` and `public`, but not `START_HERE.md`. The middleware still blocks it, so the gap is in the second layer only.
- **The portrait button is disabled for more than closed Director saving.** The contract says it "is disabled while Director saving is closed". `App.svelte` passes `canRequest = portrait_button && permissions.director.allowed && !error`, so the button is also disabled while the reader's connection has failed. In that state the hint reads "Unavailable while saving is paused.", which gives the wrong reason.
- **The reader never retries while saving is closed, although the contract describes that path.** The contract and design say a retry of an already-saved entry returns 200 "even while saving is paused, blocked, or awaiting Director direction". `Composer.svelte` disables "Retry same save" whenever `permission.allowed` is false. Instead, the reader settles an uncertain save from the next snapshot (`Session.receive`). That outcome is correct, but the helper path the contract describes is reachable only by other clients.

## Not covered by this run

- Package `PACKAGE.md` and `APPLY.md` files, the skill's other references, `docs/setup.md` and `docs/reference-hosts.md` were read only where a target document depends on them. Host hook behavior, for example the Pi example matching `cwd` exactly where the Python hooks accept subdirectories, belongs to host integrations, not these three documents.
- `docs/designs/creative-practice-examples.md`, `SITEMAP.md` and `impeccable_direction_notes.md` were left out as targets, as the distribution design's "Drift input" section directs. The examples file appears above only because the design links to it.
- No host or story was run. The observations above come from a throwaway workspace in a scratch folder that drove `helpers.bridge.Bridge` directly. They are automated-check-level evidence ([validation](../validation.md#evidence-levels)), not host observations.
