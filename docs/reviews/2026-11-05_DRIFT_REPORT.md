## docs/designs/couldhappen.md

- **Stale status in the Technical Plan.** Line 102 says "application implementation has not begun", but the header (line 4) says "implemented; current".
- **References to a section that does not exist.** Line 169 ("the later Detailed Implementation section will enumerate every concrete file and command") and line 295 ("The later implementation plan will specify reproducible dependency commands and supported versions") point to future sections. The implementation plan now lives in `docs/history/design-alternatives-and-plan.md`. `distribution-and-workspaces.md:22` also cites "Detailed Implementation step 1", which is not in this document.
- **Unsent drafts survive less than the design says (partial).** The design says drafts survive refresh, reconnect and frontend maintenance, scoped to the workspace and channel. `web/src/App.svelte` builds `new Session(sessionStorage)`. Drafts are scoped correctly but live only as long as the tab. Closing the tab or browser loses them, and nothing in the design or contract says drafts are tab-lifetime only.
- **No "resolve the existing ID first" step before an uncertain retry (partial).** The design says the browser resolves the existing ID before offering another submission. `web/src/components/Composer.svelte` shows "Retry same save" as soon as a request is pending. It forces a snapshot refresh only after the retry returns, in `finally { refresh() }`. Server-side idempotence prevents duplicates, but the pre-check is not enforced in the UI.
- **Retry of an already-saved ID is refused while saving is closed.** The design says the same ID and body return the existing saved result. In `helpers/bridge.py` `Bridge.submit`, `permission()` runs before the canonical-log identity check. A retry of an entry that was saved just before a pause, production block or `awaiting_director` mode gets 423 `saving_closed` instead of 200. The browser only recovers because the next snapshot shows the entry.
- **Checkpoint scope excludes upstream-only paths in story workspaces.** The design's checkpoint scope covers conversations, records, imports and source. `release/couldhappen.json` (the story-workspace default) excludes `docs/history/`, `docs/research/`, `docs/reviews/`, `.research/` and `goldfish_reviews/`. Any story or writer records placed under those names would silently fall outside `checkpoint check` and `writer close`. That is a leak of development layout into the story template.
- **Helper behavior with no counterpart in this design (acceptable only if it stays in setup/contract docs).** The design does not mention `checkpoint inspect --ref`, the persisted `armed` flag in `.couldhappen/control.json`, or `helpers.checkpoints.native`, the shared hook translation behind `integrations/*/stop.py`. They appear only in `docs/setup.md` and `docs/reference-hosts.md`. The design says hook configurations belong in separate materials, but nothing links the `armed` semantics back to it.

## docs/designs/distribution-and-workspaces.md

- **The workspace UUID is set by `serve`, not by `writer claim`.** Step 6 (line 65), `docs/setup.md:15` and the smoke step "claim set the workspace UUID" all attribute initialization to claim. In code, `runtime.identity` is called from `Bridge.__init__` (`helpers/bridge.py`) when `helpers serve` starts, so the UUID exists before claim. `writer claim` (`helpers/runtime.py`) only sends a `/control` request to the running helper. The smoke test passes because the helper is already running.
- **The "no enclosing Git repository" requirement is not enforced.** Line 66 says the workspace must not be initialized inside an enclosing repository, and `git rev-parse --show-toplevel` must resolve to the workspace. `helpers/checkpoints.py` `plan()` deliberately supports nested workspaces by computing a path prefix, so `checkpoint check` and `writer close` pass inside a parent repository. Only `scripts/smoke_release.py` checks this, and only before unpacking. The helpers and the skill do not.
- **Builder checks differ from the stated confirmation checklist.** `scripts/build_release.py` does not re-read the finished ZIP to confirm its exact file list matches the manifest (checklist item 2). It does not assert that the shipped `couldhappen.json` has `workspace_id: null`, that the public files are the empty templates, or that there is no real story content (items 3 and 4). Only `scripts/smoke_release.py` checks the null UUID and the absence of dev-only markers, and it does not check template content.
- **Link check is narrower than "every relative Markdown link".** The builder's `LINK` regex matches only inline `](target)` links in `.md` files. Reference-style links and HTML `href`s are not checked. A directory target such as `docs/` would fail, because only exact file paths count.
- **An undocumented scan exemption.** The builder skips the `PRIVATE_BOUNDARY_FIXTURE` marker under `tests/` and `web/tests/` (`content_pattern_allow_paths` in the manifest). The design says the scan covers "configured secret/private markers" and mentions no allowlist.
- **The release `.gitignore` is described more broadly than it is.** The design says it ignores "test screenshots" and "common OS/editor metadata". `release/.gitignore` ignores `web/test-results/` and `web/playwright-report/`, plus a short list of OS and editor files. There is no screenshot pattern as such.
- **`.codex/hooks.json` is tracked.** It is an Impeccable development hook that embeds absolute local paths. The design says development hooks stay upstream, and the manifest excludes it from the release. It still ships in the published development repository, and the design does not say whether that is intended.

## docs/public-contract.md

- **`writer release --token` does not check ownership.** The contract says it "requires matching ownership and successful full validation". In `Bridge.control` the `release` branch checks only `self.token` and the supplied token, then validation. It never checks `state['owner']` or `closing`.
- **`wait-view` and `stop` are undocumented control operations.** The `/control` handler also accepts `wait-view`, which backs `wait`. The contract describes `wait` and `stop` only as CLI commands and does not list the full operation set.
- **Error statuses outside the contract's list.** Code can return 404 `not_found`, 404 `asset_denied`, and 413 `request_too_large` for a missing `Content-Length`. The contract lists only 400, 403, 409, 413, 423 and 503, and a missing length header is not covered.
- **Retry identity versus permission order.** The contract says "Check retry identity under the file-write lock against both canonical logs" and "Resolve existing IDs first". `Bridge.submit` checks generation and permission before taking the write lock, so a retry cannot return 200 while saving is closed (see the same item under `couldhappen.json` above).
- **Undocumented CLI surface.** `python -m helpers checkpoint check|inspect`, `import-card` and `portrait` are public commands and are not mentioned in the contract. `checkpoint check` also defines the `dirty` and `clean` results that `writer close` returns. The contract mentions only that close "checks Git".
- **Vite proxy rules go beyond the contract's description.** `web/vite.config.js` also returns 403 for any request path containing an `imports`, `public`, `.couldhappen`, `.git`, `.env*` or `START_HERE.md` segment, and for any unlisted `/api/*` route. The contract says only that Vite proxies "only these routes".
